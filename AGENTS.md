# AGENTS.md

GamePort is a catalog of native Android game ports: a Go backend, PostgreSQL, and a
vanilla HTML/CSS/JS frontend with a built-in admin panel. Catalog content is entered
manually through the admin panel. An optional scheduled scraper (`cmd/scraper`) imports
new items from a few public Android-port directories, but only as **drafts**
(`published=false`) — nothing goes live without admin review.

## Layout (trust this over the README)

- `backend/` is the Go module root (`go.mod`, `cmd/server`, `internal/...`, `db/seed.sql`).
  Run all Go commands from here; the repo root has no module.
- `frontend/` holds the public UI (deployed to Vercel) and the admin UI
  (`admin.html/admin.css/admin.js`), which the backend serves from `STATIC_DIR`. No Node,
  bundler, package manager, or build step.
- `backend/db/seed.sql` is both the schema and the idempotent migration.
- `deploy/`, `.github/workflows/deploy-backend.yml`, `Caddyfile*`, `gameport.service`,
  `docker-compose.yml`, `Dockerfile` are production ops, not local dev tooling.
- Run Go commands from `backend/`; the repo root has no module.

## Commands

From `backend/`:

```bash
go vet ./...
go build ./...
go test ./...        # scraper has unit tests; api has sitemap tests
go run ./cmd/server
```

Scraper (needs a reachable DATABASE_URL; `-dry-run` writes nothing):

```bash
go run ./cmd/scraper -dry-run
go run ./cmd/scraper -only droidports
```

Full stack from the repo root: `cp .env.example .env`, set `GAMEDB_PASSWORD` and
`ADMIN_PASSWORD`, then `docker compose up -d --build` (serves on `127.0.0.1:8181`).

Running the Go server directly (needs a reachable PostgreSQL):

```bash
cd backend
STATIC_DIR=../frontend \
DATABASE_URL='postgres://gameport:pass@127.0.0.1:5432/gamedb?sslmode=disable' \
ADMIN_PASSWORD=dev go run ./cmd/server
```

- Env comes only from the process environment; there is no dotenv loader. `.env` is read
  by Docker Compose, systemd, and `deploy/manager.sh` — not by Go.
- `ADMIN_PASSWORD` (or `ADMIN_PASSWORD_HASH`) is mandatory; startup fails without it.
- `STATIC_DIR` defaults to `static` and `UPLOAD_DIR` to `uploads`, both relative to the
  working directory. From `backend/`, the UI is `../frontend`. `UPLOAD_DIR` only serves
  legacy files from the removed upload feature.
- The Compose `db` service does not publish a host port, and the backend image bakes in
  `frontend/`. For UI changes run `docker compose up -d --build`; only `uploads/` is
  bind-mounted. For host-side `go run`, point `DATABASE_URL` at your own Postgres — the
  default `GAMEDB_HOST=db` only resolves inside Compose.

## Backend conventions

- Public routes are declared once in the `publik` slice in `internal/api/server.go` and
  mounted under both `/api/v1` (current) and `/api` (legacy migration alias). Add new
  endpoints there, not directly to the mux. Safelink routes live at `/dl/...`; admin
  routes live under `cfg.AdminPath`.
- Admin auth: `wajibAdmin` returns **404**, not 401, for unauthenticated non-HTML requests,
  and redirects HTML/HX requests to `ADMIN_PATH`. This hiding is intentional. The admin
  path is secret and never linked from the public site.
- The static handler serves `STATIC_DIR` (in production only the admin assets) and
  refuses to serve `ADMIN_PATH`. It still falls back to `index.html` for extensionless
  paths, but production has no `index.html`; public `/port/{slug}` is Vercel's route.
- CORS applies only to paths starting with `/api/` and is driven by `CORS_ORIGINS`.
- There is no image upload endpoint. `image_url` is a full external URL entered in the
  admin form; `/uploads/{file}` stays read-only for files uploaded before the feature was
  removed.
- The frontend and API are split: `app.js` always targets
  `https://api.gameport.web.id/api/v1` (Vercel → API is cross-origin). Edit `API_ORIGIN`
  if domains change, add the new origin to `CORS_ORIGINS`, and keep using `asetAPI()` for
  database-stored relative image paths.
- `/port/{slug}` and the long-tail landing pages `/genre/{slug}`, `/platform/{slug}`,
  `/kategori/{slug}` are frontend routes (Vercel rewrites in `frontend/vercel.json`),
  not API routes. Per-page SEO tags (title, description, canonical, Open Graph,
  JSON-LD) are written by `app.js` after the API responds.
- `/sitemap.xml` is generated by the backend (`internal/api/seo.go`, from the DB) and
  proxied by a Vercel rewrite; `frontend/robots.txt` points at it. `PUBLIC_URL`
  (default `https://gameport.web.id`) controls the absolute URLs in it. Social preview
  image: `frontend/og-default.png`. Vercel Root Directory must be `frontend`.
- Scraper lives in `internal/scraper` (`cmd/scraper`). It reads enabled rows from
  `scrape_sources`, honours robots.txt + `Crawl-delay`, sends a clear User-Agent, and
  always creates drafts (`published=false`). Supported `kind`s: `rss`, `playported`,
  `markdown`; a new site needs a parser in `internal/scraper` and a matching value in the
  `kind` CHECK constraint. Dedupe is `scrape_items(source_slug, external_id)` plus a
  title/source-URL check across sources — keep both, or cron will recreate rows daily.
  There are no download URLs in scraped drafts; `source_url` points at the reference page.
  Run it via `deploy/scrape.sh` (loads `.env`) and `gameport-scraper.timer`.

## Database

- `backend/db/seed.sql` is the single source of schema. Compose runs it only when the data
  volume is empty; `deploy/deploy.sh` reapplies it on every deploy, so it must stay
  idempotent.
- For schema changes, add idempotent statements (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`,
  `CREATE TABLE/INDEX IF NOT EXISTS`) and keep reference seeds using `ON CONFLICT`. Editing
  only an initial `CREATE TABLE` will not migrate existing databases.
- `v_port_detail` (flattened joins/platform array) and `v_statistik` (homepage aggregates)
  are dropped and recreated on every seed run. Prefer querying them over re-joining tables.
- `scrape_sources` (one row per site) and `scrape_items` (dedupe log) back the scraper.
  Seed sources use `ON CONFLICT (slug) DO NOTHING` so operator edits survive deploys. All
  scraped ports are inserted with `published=false` and the source's default
  `category_slug`/`status_slug`; review them in the admin list before publishing.

## Deploy and ops (do not run from a dev checkout)

- Current production is artifact-based and needs no git clone or Go on the server.
  `.github/workflows/deploy-backend.yml` runs `deploy/package.sh`, publishes a GitHub
  Release (`gameport-backend-linux-amd64.tar.gz`, `SHA256SUMS`, `version.txt`), and
  `deploy/autodeploy.sh` on the VPS polls `releases/latest/download/version.txt` every
  two minutes. It only packages the backend, admin static, seed, and deploy scripts —
  the public frontend stays on Vercel.
- `deploy/deploy.sh <artifact-dir>` installs the artifact into
  `/opt/data/workspace/deployed/game-port`, preserves `.env` and `uploads/`, restarts the
  supervisor, applies `seed.sql`, runs health/admin/API checks, and rolls back on failure.
  `deploy/manager.sh` still runs inside the Hermes container (Postgres over a unix socket,
  app on `0.0.0.0:8181`). `deploy/package.sh` is the only script that needs Go.
- Scraper schedule is a separate host timer (`gameport-scraper.service`/`.timer`), enabled
  manually like the auto-deploy timer; `deploy.sh` only refreshes the copies in the deployed
  folder. It calls `deploy/scrape.sh` via `docker exec` because `.env` is not inherited by
  `docker exec`. Scrape output is always drafts, so a failed run is non-critical.
- `.env` lives only on the server, is never in Git or a release artifact, and is not
  touched by `deploy.sh`. `manager.sh` sources it; values containing `&` or `?` must be
  quoted there. Change `.env` then `manager.sh restart`.
- Caddy variants: `Caddyfile.domain` is the current `api.` + `vps.` setup (apex and `www`
  are Vercel; it hardcodes container IP `172.18.0.3`), `Caddyfile` is a single-domain
  template, `Caddyfile.ip` serves raw HTTP on `:80`. Never add an apex/`www` block while
  its DNS points to Vercel, and never use a bare IP as a Caddy site address — Caddy forces
  HTTPS with a 308.
- `systemctl reload` does not reread `.env` (use `restart`), and a running binary cannot be
  overwritten. Caddy config is installed manually on the host; `deploy.sh` only refreshes
  the copy in the deployed folder.
- Deploy guide: `deploy/README.md`. Older host/systemd notes live in `README-DEPLOY.md`;
  DNS/HTTPS notes in `SETUP-DOMAIN.md`.

## Style

- Comments, UI strings, and many identifiers are Indonesian (`wajibAdmin`, `AmbilSetting`,
  `tampilLogin`). Match the surrounding style instead of translating.
- Commits use Conventional Commits (`feat(api): ...`, `fix(publik): ...`). There is no CI
  or linter config; verify with `go vet ./...`, `go build ./...`, and the health/curl
  checks in `deploy/deploy.sh` when a change affects serving.
- Never commit secrets; only `.env.example` is tracked. `.gitignore` excludes `.env*`,
  `uploads/*`, logs, and local DB/state files. Schema changes belong in
  `backend/db/seed.sql`.
